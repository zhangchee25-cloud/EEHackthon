# 论文阅读辅助网站搭建基础知识

面向黑客松小组的前后端架构与文件修改指南

日期：2026年10月17日　适用对象：没有系统学习过网站开发的小组成员

## 1 先建立网站的整体概念

这份文档对应小组第三项分工：了解网站前后端的基础架构、常见文件的职责，以及手动修改界面文字的方法。读完后，应当能够看懂一个网站项目的大致结构，判断修改应该发生在哪里，并与负责开发的组员沟通。

**先记住这句话：HTML 描述页面内容和结构，CSS 决定外观，JavaScript 处理交互；后端负责服务端业务处理，并按需要连接数据库、文件存储和模型服务。**

本文以论文阅读辅助网站为例说明概念。目录、功能和接口均为教学示例，不代表小组已经确定技术方案；当前只整理知识文档，不创建网站或业务代码。

### 1.1 最常见的几个名词

| 名词 | 用容易理解的话解释 | 在本项目中的例子 |
| --- | --- | --- |
| 网页与网站 | 网页是一个页面；网站由相互关联的页面和功能组成 | 上传页、阅读页、历史记录页 |
| 浏览器 | 获取网页资源并呈现界面的软件 | Chrome、Safari、Edge |
| 前端 | 用户在浏览器里看到并操作的部分 | PDF 阅读区、提问框、按钮 |
| 后端 | 接收请求并执行服务端业务的部分 | 解析论文、调用模型、保存记录 |
| API 接口 | 程序之间约定的请求与返回方式 | 提交问题，返回答案和引用 |
| 数据库与文件存储 | 分别适合保存结构化记录和文件等对象 | 笔记与论文信息；原始 PDF |

“前端”和“后端”首先是职责划分，不要求部署在两台不同的电脑上。开发时它们可以同时运行在一台电脑；某些框架也会把两部分放在同一项目中。浏览器和服务器通过请求、响应交换资源或数据。[2]

### 1.2 静态页面与完整应用的区别

静态页面适合展示介绍、布局和固定示例。它也能通过 JavaScript 提供浏览器内的交互，但单靠一份 HTML 文件，不会自动具备论文解析、调用受保护的模型服务、跨设备保存记录等能力。

对于本项目，可以先用静态界面确认布局，再接入真实接口。演示用固定答案或模拟数据时，应在团队内明确标注，避免把界面已完成误认为完整功能已完成。

**阅读路线：**第 2—3 节建立前端基础；第 4—5 节理解架构和文件；第 6 节直接用于修改 UI 文字；第 7—8 节用于联调和组内交接。

## 2 HTML 负责页面内容和结构

HTML 的全称是 HyperText Markup Language，中文通常称为超文本标记语言。它用“标签”描述内容的含义，例如标题、段落、链接、按钮和输入框。它主要表达结构，不负责完成复杂业务逻辑。[1]

### 2.1 一份 HTML 文档包含什么

| 部分 | 负责什么 | 初学者需要知道的事 |
| --- | --- | --- |
| 文档类型声明 | 声明使用现代 HTML 文档模式 | 通常位于文件最前面 |
| html | 整份文档的根元素 | 可用 lang 标明页面主要语言 |
| head | 字符编码、页面元信息及资源引用 | 通常不是页面正文 |
| title | 浏览器标签页中的标题 | 与页面里显示的大标题不是同一个位置 |
| body | 用户实际看到的页面内容 | 导航栏、阅读区、按钮等放在这里 |

标签通常有开始和结束部分，并且可以嵌套；有些元素没有结束标签，例如图片元素。属性为元素补充信息，例如链接的目标、图片的位置和输入框的提示。

### 2.2 读项目时最值得认识的标签

| 标签或属性 | 作用 | 论文阅读网站中的例子 |
| --- | --- | --- |
| h1 到 h6、p | 标题层级与段落 | 页面标题、论文简介 |
| header、nav、main、aside | 标记页面不同区域的语义 | 顶部栏、导航、正文、侧边栏 |
| div、span | 通用容器 | 将若干内容组织成一组 |
| a、href | 链接及目标地址 | 打开论文原文 |
| button | 触发操作的按钮 | 上传、生成摘要、发送问题 |
| input、textarea、label | 单行输入、多行输入及说明 | 论文搜索框、提问框 |
| class、id | 分类标记和标识符 | 供样式、脚本或页面定位使用 |

**理解语义比背标签更重要。**能用按钮表达的操作就使用按钮，输入框应有明确说明。这样更容易使用键盘操作，也方便辅助工具理解页面。

### 2.3 修改文字时要区分三种位置

**可见正文：**页面大标题、“生成摘要”等按钮标签，通常来自标签内容或组件中的文字。

**元素属性：**输入框里灰色的提示通常来自 placeholder；图片说明来自 alt；这些与正文是不同位置。placeholder 不能代替始终可见的输入说明。

**浏览器标题：**标签页里的“论文助手”通常来自 title，或框架提供的页面元信息配置。只修改页面大标题，标签页标题未必随之改变。

## 3 CSS 和 JavaScript 各自负责什么

### 3.1 CSS 决定页面如何呈现

CSS 是层叠样式表，用于设置字体、颜色、尺寸、间距和布局。理解“选择器找元素，样式规则改外观”即可开始阅读项目。[3]

| 概念 | 含义 | 在本项目中的用途 |
| --- | --- | --- |
| 选择器 | 指定一条样式作用于哪些元素 | 只调整上传按钮的样式 |
| 盒模型 | 内容、内边距、边框、外边距 | 理解卡片为什么占这么大空间 |
| Flex 布局 | 适合沿一个主要方向排列内容 | 顶部工具栏、按钮组 |
| Grid 布局 | 适合按行列安排区域 | 左侧论文、右侧问答的工作区 |
| 响应式布局 | 根据可用空间调整排列与尺寸 | 小屏幕下把左右两栏改为上下排列 |
| 样式优先级与继承 | 多条样式共同决定最终外观 | 排查改了颜色却没有变化 |

修改布局时，先看父容器如何分配空间，再看子元素的宽度和间距。CSS 中的 width、padding、margin 分别涉及宽度、内边距、外边距；混淆它们很容易让页面挤在一起或超出屏幕。

样式可能存在于独立 CSS 文件、组件专用样式文件，或组件中的样式类名中。例如采用工具类样式方案的项目，尺寸和颜色可能直接由组件上的类名表达。

### 3.2 JavaScript 让页面响应操作

JavaScript 可以响应点击、读取输入、发送网络请求并更新页面内容。DOM 可以理解为浏览器中的页面结构；脚本能够读取和修改它。使用组件框架时，通常通过更新数据和状态来驱动界面变化。[4]

以“生成摘要”按钮为例，交互至少需要考虑：是否已经选择论文、是否正在请求、成功后显示什么、失败后如何提示和重试。按钮文字可能随状态变化为“生成中…”，因此不一定只有一处需要修改。

### 3.3 React 与 TypeScript 在这里扮演什么角色

React 是用于构建界面的 JavaScript 库。它把页面拆成可组合的“组件”，例如上传区、阅读区和问答区。组件通常写在 .jsx 或 .tsx 文件中，因此 React 项目的界面文字往往不在 index.html 里。[5]

TypeScript 在 JavaScript 基础上增加类型检查；常见文件后缀为 .ts，包含 JSX 界面描述时常用 .tsx。它有助于提前发现数据使用错误，但不等于后端，也不会自动生成接口。

**按修改目的判断：**改按钮文案，找内容来源；改颜色和布局，找样式；改点击行为，找事件处理；改模型生成结果，继续检查后端处理和模型输入。一次改动可能涉及多个位置。

## 4 用论文阅读流程理解前后端架构

### 4.1 一次提问如何经过整个系统

**用户在浏览器操作 → 前端发送请求 → 后端处理 → 按需要读取文件和数据并调用模型 → 后端返回结果 → 前端显示答案和出处。**

这是帮助理解职责的简化流程。后端可能采用独立服务，也可能采用同一框架中的服务端接口或托管函数；不论采用哪种形式，浏览器侧和服务端的职责仍需区分。

1. **选择论文。**前端提供文件选择和上传反馈。浏览器里选中文件，并不表示服务器已经收到文件。
2. **上传与校验。**后端接收文件并检查允许的格式、大小等条件，按方案保存原始文件，返回可用于后续操作的论文标识。
3. **提取内容。**解析模块提取文本和必要的页码信息。扫描版 PDF 可能需要 OCR；双栏、公式和表格也可能影响解析质量。
4. **提交问题。**前端把论文标识、问题，以及约定的上下文发送给后端，而不是只发送一句脱离论文的问题。
5. **组织模型输入。**后端根据方案选择全文、选中段落或检索到的相关片段，再调用模型。长论文不一定适合直接整篇传入。
6. **呈现与保存。**前端展示答案、相关原文和定位信息；需要历史记录时，再由相应存储方案保存。

### 4.2 各部分的职责边界

| 部分 | 核心职责 | 不能仅凭什么判断已经完成 |
| --- | --- | --- |
| 前端界面 | 展示、输入、交互、加载和错误状态 | 页面上已经有上传按钮 |
| 后端接口 | 参数校验、任务组织、模型调用 | 接口地址已经写进配置 |
| 解析与定位 | 提取内容并保留来源映射 | PDF 已能在浏览器里打开 |
| 文件与数据存储 | 保存 PDF、论文信息、问答或笔记 | 刷新前还能看到记录 |
| 模型服务 | 根据输入生成摘要或回答 | 已收到一段通顺的回复 |

**PDF 能显示不等于文字已经解析。**前端阅读器负责呈现文件，解析模块负责获取可供处理的内容，两者要分别验证。

**显示页码不等于引用可靠。**应让回答与实际传入的原文片段、页码或位置建立对应关系；不要仅依赖模型自行生成出处。PDF 文件页序也可能与论文印刷页码不同。

### 4.3 数据保存需要单独设计

“当前页面中的数据”“当前浏览器保存的数据”和“服务器长期保存的数据”是不同层次。仅放在页面内存中的问答可能随刷新丢失；浏览器本地保存通常不会自动跨设备同步。是否需要数据库，应根据历史记录、用户和协作需求决定。

## 5 常见文件和目录的职责

文件名是约定，不是统一标准。下面是阅读项目时的辨认示例，不是需要立即建立的目录，也不是当前仓库已存在的结构。最终应以项目说明、依赖和实际引用关系为准。

### 5.1 简单原生前端通常有哪些文件

| 文件或目录 | 主要职责 | 常见修改 |
| --- | --- | --- |
| index.html | 页面入口和静态内容结构 | 大标题、按钮文字、输入提示 |
| styles.css | 外观和布局 | 配色、字体、两栏比例、间距 |
| app.js | 浏览器交互和网络请求 | 点击按钮后的操作、状态切换 |
| assets/ | 图片、图标、字体等资源 | Logo、背景图 |

### 5.2 使用组件和后端时还会出现哪些文件

| 文件或目录示例 | 主要职责 | 阅读时的关注点 |
| --- | --- | --- |
| src/main.tsx | 前端初始化入口 | 整个界面从哪里挂载 |
| src/App.tsx | 顶层界面组合 | 页面如何组合各个区域 |
| src/components/ | 可复用界面组件 | 上传区、按钮、问答框 |
| src/pages/ 或 src/routes/ | 页面与路由组织 | 不同网址分别显示什么 |
| src/styles/ | 全局或局部样式 | 布局与视觉规则 |
| src/locales/ 或 src/i18n/ | 多语言文案资源 | 显示文字对应哪个文案键 |
| src/services/ 或 src/api/ | 前端调用接口的封装 | 请求地址、参数和结果处理 |
| server/ 或 backend/ | 服务端业务 | 上传、解析、模型调用与存储 |
| public/ | 某些工具中的静态资源目录 | 文件如何被公开访问 |

### 5.3 配置文件也需要认识

package.json 通常记录 JavaScript 项目的依赖和运行任务；锁文件记录解析后的依赖信息。Python 后端可能使用 pyproject.toml 或 requirements.txt 管理依赖。README.md 应说明项目如何启动和协作。

.env 类文件用于配置环境变量；是否会暴露给浏览器取决于工具和使用方式，不能只看文件名。以 Vite 为例，VITE_ 前缀变量会进入客户端构建结果，因此不能放模型密钥。[6]

.gitignore 指定哪些文件不纳入 Git 跟踪。node_modules/ 通常是安装的依赖，dist/ 或 build/ 通常是生成产物；日常修改优先寻找源文件。实际名称仍取决于项目工具。

**看到 app、pages、api 等名称时先确认框架。**例如，全栈框架中前后端可能都在一个项目内；某个 api 目录可能存放服务端处理，也可能只是前端请求封装。

## 6 手动修改 UI 文字的实用方法

UI 即用户界面。修改前先判断文字属于哪一种来源：写死的静态文字、随状态变化的文字、多语言资源，还是接口返回的数据。

### 6.1 想改什么应该去哪里找

| 想修改的内容 | 优先寻找的位置 | 修改时注意 |
| --- | --- | --- |
| 页面标题或介绍文字 | HTML、页面文件、组件或语言文件 | 区分页面标题与标签页标题 |
| “上传论文”等按钮文字 | 对应组件及其状态分支 | 同时检查上传中、失败等状态 |
| 输入框的灰色提示 | placeholder 或组件属性 | 另保留清楚的输入说明 |
| 顶部导航文字 | 导航组件或菜单配置 | 不要误改跳转路径 |
| 摘要区的栏目名 | 页面组件或语言文件 | 栏目名与生成内容来源不同 |
| 模型回答或论文标题 | 接口响应、数据或后端处理 | 修改页面占位文字未必有效 |
| 颜色、字号和两栏比例 | CSS、样式模块或组件类名 | 检查长文字是否撑坏布局 |

### 6.2 一套可重复的定位流程

1. **记录原文和位置。**例如“阅读页右侧面板中的‘开始分析’按钮”，并记下是初始状态还是加载状态。
2. **在源文件中全局搜索原文。**先搜索完整文字；没有命中，再搜索关键片段。优先查看源代码和语言资源，避免直接修改构建产物。
3. **读清上下文。**确认命中的是实际显示位置，还是注释、示例、测试或未使用组件。同样的文字也可能出现多次。
4. **判断是否为变量。**若页面引用了按钮文案变量或多语言文案键，应继续追踪它的定义；若文字来自接口，就检查接口返回。
5. **只改显示内容。**保留引号、括号、标签、属性名、变量名和接口字段；这些可能决定程序是否正常运行。
6. **查看页面验证。**确认改动出现，并检查加载、成功、失败状态和窄屏布局。共享组件的修改还要检查其他使用它的位置。

### 6.3 搜不到或改了没有变化怎么办

**搜不到：**文字可能由多个片段拼接、通过翻译键映射，或由服务器返回。打开浏览器开发者工具的 Elements（元素）面板查看显示位置，再用 Network（网络）面板判断是否来自接口。

**改了没变化：**先确认打开的是正确项目和网址，再检查是否保存、是否命中了实际使用的文件。线上页面还需要重新构建部署；前端环境配置的修改也可能需要重启或重新构建。

**不要把临时改动当作源码改动。**开发者工具中直接改页面文字，只影响当前浏览器显示，刷新后通常会恢复，不会自动写回项目文件。

## 7 接口联调与上线的基础知识

### 7.1 接口是前后端需要共同遵守的约定

接口约定至少说明：地址、请求方法、输入字段、返回字段、错误情况。GET 常用于读取数据，POST 常用于提交或触发处理；JSON 是常见的数据交换格式，文件上传则常用 multipart/form-data。[2]

下面仅用于讨论分工，地址和字段均未实现。

| 目的 | 示例接口 | 提交内容 | 返回内容 |
| --- | --- | --- | --- |
| 上传论文 | POST /api/papers | PDF 文件 | paper_id、处理状态 |
| 查询解析进度 | GET /api/papers/{id}/status | 论文标识 | 状态、可读错误信息 |
| 提交问题 | POST /api/questions | paper_id、question | answer、citations |

处理较慢时，可以采用“先返回任务标识，再查询进度”的方案；也可以按需求使用流式返回等方式。选择一种与时间和技术条件相符的方式，并让前端状态与接口一致。

### 7.2 本地运行不等于上线

localhost 指当前访问者自己的电脑。队友在自己的电脑上打开同一个 localhost 地址，不会自动进入你的服务。不同端口也可能对应不同服务，不能把前端地址与后端地址混用。

开发服务器便于本地预览；构建将源文件处理为可发布资源；部署则让相应服务和资源能够在目标环境运行。只发布前端文件，不会自动部署另一个后端或数据库。上线后还要确认接口地址、环境配置及数据存储有效。

### 7.3 常见问题怎样初步定位

| 现象 | 优先检查 | 通常需要谁协助 |
| --- | --- | --- |
| 按钮点击无反应 | Console 控制台报错、按钮是否禁用、事件是否绑定 | 前端 |
| 请求出现 404 | 请求地址、路径、部署路由是否对应 | 前后端一起 |
| 请求出现 500 | 后端日志、解析或模型服务错误 | 后端 |
| 出现 CORS 提示 | 前后端来源及服务端允许规则 | 后端与部署负责人 |
| 一直显示处理中 | 是否超时、后端状态、前端是否收到结束结果 | 前后端一起 |
| PDF 可打开但回答为空 | 文本是否提取成功、问题是否绑定正确论文 | 解析与后端 |

CORS 是浏览器针对跨来源请求的机制；来源由协议、主机和端口等确定。开发代理或正确的服务端响应配置可以按方案处理跨域问题，不应要求用户关闭浏览器安全检查。[7]

**模型密钥放在服务端。**浏览器可访问的脚本和资源都不适合保存密钥。前端调用自己的服务端接口，再由服务端访问需要密钥的模型服务。[6]

## 8 组内交接与学习重点

### 8.1 开发前需要共同确认的事项

- 采用原生 HTML、CSS、JavaScript，还是使用组件框架；这是实现选择，不是功能本身。
- 上传、阅读、摘要和问答分别由哪些页面或组件承载，哪些状态需要显示。
- 前端与后端如何交换论文标识、问题、答案和引用信息。
- PDF 是否要长期保存，问答刷新后是否保留，是否需要登录和跨设备同步。
- 论文解析、页码定位和模型回答各由谁负责验证。
- 项目如何启动、配置和部署，说明统一记录在哪里。

### 8.2 修改界面文字前后的检查

修改前确认文字来源和使用范围；修改后确认页面能够打开、文字已经更新、按钮仍正常工作，并检查长文字、窄屏以及加载和失败状态。对摘要和答案，另行核对数据来源；对引用，实际点击验证能否回到正确原文位置。

### 8.3 建议按这个顺序学习

**第一步，认识内容结构。**看懂 HTML 的标题、段落、按钮、输入框和主要属性，能区分页面正文、浏览器标题和提示文字。

**第二步，认识样式。**理解选择器、盒模型和两栏布局，知道文字变化为什么可能影响宽度和换行。

**第三步，认识交互和请求。**理解按钮事件、页面状态、API 与 JSON，能够用开发者工具查看一次请求是否成功。

**第四步，阅读团队实际项目。**从 README 找启动方法，再找入口、页面、组件、样式与接口文件。先确认一个文字的来源，再逐步认识其余部分。

### 8.4 可以直接用于组内汇报的表述

我们负责的网站基础架构可以分为浏览器里的前端和处理业务的后端。HTML 管内容结构，CSS 管外观，JavaScript 管交互；后端接收论文和问题，组织解析、模型调用与存储。改界面文字时先全局搜索原文，再判断它在 HTML、组件、语言文件还是接口数据中。对论文助手，要分别验证 PDF 展示、文本解析和引用定位，不能只看页面是否漂亮、回答是否通顺。
